# ADR-0013：雙語內容以欄位層 JSON 存放

日期：2026-10-12
狀態：Accepted

## 背景

食譜、菜單、食材的文字之後要有中英兩種語言，而且之後由 LLM 匯入時會一次產生兩種語言。同一道食譜的結構（數量、單位、步驟順序、食材引用）不分語言，只有文字不同。只有兩種語言、只有一個人使用，資料量小。

## 決策

- 需要雙語的文字欄位在資料庫存成 JSON：`{ en?: string, zh?: string }`（`LocalizedText`）；有片段的文字（菜單描述、步驟）每種語言各存一組片段，因為兩種語言的斷句不同。
- Prisma 的 `Json` 沒有型別，資料存取層一律用 zod 解析後才交給元件。
- 畫面用 `localize(text, locale)` 取值，缺的語言退回另一種。
- 不分語言的資料（數量、單位、時間、價格、id）維持一般欄位。
- 用量的單位不存翻譯，顯示時由程式碼的單位清單對應各語言的寫法。

## 考慮過的替代方案

- 翻譯表（`RecipeTranslation(recipeId, locale, …)`，Saleor、Django-parler 的做法）：可依語言查詢與建索引，語言多時好擴充；但步驟、用量、群組每一層都要一張翻譯表，兩種語言用不到它的好處。
- 每種語言存一份完整資料、以群組 id 串起來（Strapi、WPML 的做法）：適合各語言內容差很多的情況；這裡會讓中英兩份的數量與步驟各自漂移。
- 只存一種語言，需要時請 LLM 翻譯並快取：省欄位，但離線或沒有 API 金鑰時看不到另一種語言，也無法手動修正翻譯。

## 後果

- SQLite 不方便直接搜尋或排序 JSON 內的文字；目前資料量小，用程式過濾。之後真的需要再加衍生欄位或改翻譯表。
- 新增需要翻譯的欄位時，型別用 `LocalizedText`，並在資料存取層的 zod schema 加上對應解析。
- 要加第三種語言時，JSON 加一個 key 即可，但要回頭補資料。
