# ADR-0026：匯入的食材對應改由程式比對，LLM 只整理食譜

日期：2026-10-14
狀態：Accepted

## 背景

ADR-0022 的匯入只呼叫一次 LLM：把整份食材目錄（id、名稱、別名）連同原文一起送出，由模型同時整理食譜並決定每行用量對應哪個食材。實際使用遇到幾個問題：

- 比對完全交給模型，結果不穩定：寫錯 id、該新增的漏掉、同一個食材這次對上下次沒對上。
- 目錄會越來越大，清單越長，模型越容易漏看或對錯；每次匯入也都要送整份目錄。
- 一次要做的事太多（整理、翻譯、拆步驟、引用用量、對應食材、估營養），整理食譜的品質也受影響，曾經只輸出第一個步驟。

整理食譜（份量、步驟、翻譯、步驟引用用量）與目錄無關，兩件事可以分開。食材確認卡本來就由使用者確認每一行，不確定的情況交給使用者判斷即可。

## 決策

匯入分成兩段，只呼叫一次 LLM：

1. **整理食譜（LLM）**：只送原文，不送目錄。每行用量除了原本的欄位，另外給：
   - 標準名稱（中英，照食譜用的形態，例如黑胡椒粒），不含切法等處理方式；
   - 幾個搜尋用的同義詞（中英都要）；
   - 每 100 g 的營養估計（熱量、蛋白質、碳水、脂肪）；
   - 或標記為非食材（例如煮麵用的水）。
2. **程式比對**：用標準名稱、同義詞與原文寫法，正規化後（大小寫、前後空白、英文複數、標點）比對目錄的名稱與別名。每一行得到其中一種結果：

| 結果 | 條件 | 食材確認卡 |
| ---- | ---- | ---- |
| Matched | 原文寫法就是某個食材的名稱或別名 | 直接連上，摺疊在下方 |
| Alias | 只有一個食材相符，但原文寫法不是它的名稱或別名 | 連上，預設勾選加為別名（同現況） |
| Suggested | 有多個食材相符 | 預先選最可能的一個（相符程度最高者），下拉選單最上面列出其餘候選 |
| New | 沒有食材相符 | 新增食材，名稱、別名、營養用第 1 段給的值；另外列出寬鬆比對（部分字詞重疊）找到的「可能是」，方便改連 |
| Not linked | 第 1 段標記為非食材 | 不連結 |

食材確認卡之後的流程、存檔與資料模型不變。比對規則與候選數放 `src/features/recipe-import/` 的設定檔。

## 考慮過的替代方案

- 維持一次呼叫、送整份目錄（現況）：最簡單，但目錄變大後不準、不穩定，也無法單獨改進比對。
- 程式比對後，不確定的行再呼叫一次 LLM 判斷（只送候選）：使用者要處理的較少，但多一次呼叫、多等 5 到 10 秒，部分結果又回到由模型決定；個人使用時，在確認卡多點一下的代價更小。之後若手動處理太多，可以再加回來，資料結構不用改。
- 語意搜尋（embedding）取代程式比對：同義詞找得到，但 Anthropic 沒有 embedding API，要再接一個外部服務；個人規模用不到。

## 後果

- 取代 ADR-0022「目錄隨原文送給模型、由模型對應食材」的部分；其餘（SDK、Haiku 5.5、structured outputs、只產生草稿、Route Handler、一次呼叫）不變。
- 每次匯入固定一次呼叫；不送目錄，輸入略少；每行都估營養，輸出每份食譜約多 300 token（約 US$0.00015），只有新食材會用到。
- 比對結果由程式決定，同樣的輸入每次結果相同，可以用假資料測試。
- 比對能否找到，取決於第 1 段給的同義詞；字面完全不同又沒列進同義詞的（例如 scallion 與蔥）會變成 New。由確認卡的「可能是」與使用者改連補救；改連時加為別名，之後就能直接對上，目錄越用越準。
- 需要新的比對模組（純函式）、改寫輸出格式與 prompt，食材確認卡多一個 Suggested 狀態與「可能是」清單。
- 第 1 段的 prompt 一併修正實測發現的問題：每一步都要輸出、清單已有的食材不在步驟裡重複加一行、提示不是步驟。
